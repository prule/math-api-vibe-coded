Vibe coding vs OpenSpec

The same PRD, domain model, standards and backlog prompts, built twice by one agent on Claude Opus 5.5. One build planned every change in OpenSpec first; the other went straight from the backlog prompt to code. Both then ran the same code reviews, wrote retrospectives and merged by PR on green CI. The first comparison stopped at item 5. A second round then took both builds through items 5a, 6 and 7, each in a fresh session.

What the reviews caught

openspec's plan review raised 4 points:

  • a webjar 404 check that could pass for the wrong reason
  • BR-6 "after normalisation" untested (1.00^999 must succeed)
  • a "worst operands" scenario without an expected result
  • a missing task for the unary response, which would have thrown a NullPointerException

Its code reviews added 17 more, mostly docs and test gaps such as negative-exponent BR-6 and b undocumented as optional.

vibe's reviews made three main catches:

  • Ponytail: its first real code-level catch in this project. The "round once" POWER test could not fail, because BigDecimal.pow(n, DECIMAL128) passes it while being wrong in the last digit for some inputs. Ponytail found a case that tells the two apart, 0.2857142857142857142857142857142857^668.
  • Spec reviewer: request b wasn't nullable in the docs schema.
  • Both reviewers: PRD and DOMAIN-MODEL side claims had drifted.

Both builds independently flagged the same STANDARDS §6 gap: no row for profile tests.

None of the plan-review catches showed up as a difference in shipped behaviour. The vibe build gets 1.00^999 = 1, unary responses and the webjar 404 right without them, and all 36 new probes match. In this round the plan review made the OpenSpec build's tests stronger, but it didn't prevent a bug the vibe build shipped.

The open design decision wasn't open

Item 7's prompt asks for a design decision: whether arity lives on the enum or in separate types, and whether b is optional or rejected. Both builds made the same choices: arity() on each Operation constant, b null for unary Operations, BR-9 checked before BR-1, and b left out of unary responses. DOMAIN-MODEL §2 and PRD §3.2 already describe that final design, so the docs carried it, as the backlog did for items 1–5.

Living specs and the audit

  • Regressions: none in either build. The item 1–5 probes return the same status and type, and the detail-text changes are the ones each PR announced. The tests guarded old behaviour in both builds, so the OpenSpec specs can't be credited with preventing a regression that never happened.
  • Milestone audit: only the OpenSpec process has one. Its whole-repo audit before item 6 flagged the same input class as the BR-1 bug (1e2147483648). In that build the input already returns a 400, so the audit skipped it as a classification nit. The vibe build has no audit step, and its 500 for that input survived three more items.
  • Session behaviour: the vibe session stopped twice while background reviewers or CI were still running, and needed a nudge to continue. The OpenSpec session needed none. The OpenSpec build's CLAUDE.md says to run every step without waiting to be asked. The vibe build's CLAUDE.md doesn't say that, so this comes from how the instructions are worded, not from OpenSpec itself.

Round 2 verdict

The pattern held, and the case for OpenSpec got weaker. OpenSpec still cost about 1.5× the time and tokens, and still produced more tests (261 against 152). This time, though, it caught nothing that the vibe build shipped, and the two builds behave identically on every new case. With docs that already describe the finished design, OpenSpec's plan mostly restates them. Its value here comes down to stronger tests and a written rationale.

Short answer

OpenSpec added some value here, and it cost about 50% more time. The OpenSpec build spent 49.6 active minutes on items 2–5 and the vibe build 32.6, with 39% more output tokens. In return it has 129 tests to 73, 94% branch coverage to 80%, and it caught a real BR-1 bug that the vibe build shipped. That bug is an operand like 1E+2147483648, which slips past the range check. Both builds wrote the bug, and in both the cause was Math.abs on a scale of Integer.MIN_VALUE. OpenSpec's code reviews checked the code against a design that spelled out the comparison, and caught it. The vibe build's three reviews had no design to check against, and missed it.

On everything else the two came out level. They ended with the same architecture and the same Sonar result (quality gate passed, 0 vulnerabilities, 0 duplication). They agreed on status and type in 24 of 28 live probes. The vibe build was stricter in two of the four disagreements, and its error details are more specific.

Without a plan to review, the vibe build's code reviews found about as much as both stages did in the OpenSpec build: 40 findings against 45. The spec reviewer did most of the work. It ran the real jar and compared responses with the PRD, and found every contract bug the vibe build fixed:

Ponytail found nothing in items 1–3. Its one solo finding was a minor error-type edge, and its one shared finding was the copied error message in item 5.

The bug only OpenSpec caught

BR-1 caps an Operand's scale at ±1000. Both builds wrote the check with Math.abs(scale). new BigDecimal("1E+2147483648") has scale Integer.MIN_VALUE, and Math.abs of that is still negative, so the operand passes. In the vibe build the request then fails inside BigDecimal with ArithmeticException: Overflow and returns 500 where the PRD promises 400 operand-out-of-range. The catch-all handler means no internals leak and the server does no heavy work.

In the OpenSpec build, design.md stated the rule as two comparisons. The agent "simplified" them to Math.abs while implementing, and both code reviews flagged the gap between design and code. The vibe build had no design to diverge from. All three of its reviews read the Math.abs line as correct.

Retrospectives

What each build learned

vibe

  • Test the wrong JSON type, not only the wrong value (item 2).
  • Check what unit a library limit counts: digits or characters, bytes or characters. Test at limit+1 for every input shape (item 4).
  • Check framework defaults with a test: Spring 7's null ProblemDetail.type, Jackson coercion (item 2).
  • Test that docs examples equal real responses (item 5).

openspec

  • Check framework defaults before planning (items 1, 2, 4, 5).
  • Never derive a test's expected value from the code under test (item 3).
  • Implement a planned condition exactly as written, and test int ranges at MIN_VALUE and MAX_VALUE (item 4).

The lesson both builds recorded most often was the same: Spring 7, Jackson 3 and springdoc defaults surprised the agent in each one. OpenSpec didn't prevent those surprises. Its plan review sometimes caught them earlier, and in the vibe build they turned up as failing tests during the build. Neither build has yet turned a repeated lesson into a change to its process.

Caveats

What makes this comparison unfair

  • One run each. The same model can write the same bug and then catch it or miss it by chance. The BR-1 result is one data point, not a rate.
  • The prompts were already detailed. The backlog prompts spell out the design, which leaves less for OpenSpec's propose step to add. With vaguer prompts, OpenSpec could matter more.
  • Different sessions. The vibe build ran in one long session that also handled setup and this comparison. The OpenSpec build also ran in one session, and its log includes setup in item 1. Cache figures depend on how much context each session had built up.
  • Findings were counted differently. The vibe tally includes judgement calls that weren't acted on. The OpenSpec tally comes from its retrospectives. "40 against 45" shows how much each build looked at, not how many bugs each found.
  • The vibe build was written after the OpenSpec build existed, with the same model, from the same docs. The agent didn't read the OpenSpec code or the earlier report until this comparison, but the shared docs already contained many decisions that build had made.
Takeaways

So, does OpenSpec add value?

  1. Some, mainly as a reference for reviewers. The written design gave the code reviews something exact to compare against, and that is how the BR-1 edge was caught. Without it, three reviews read the same faulty line as correct.
  2. It also produces more tests. Each spec scenario became a test: 129 against 73, and branch coverage of 94% against 80%. That is the clearest quality difference Sonar shows.
  3. It costs about 1.5× the time and 1.4× the output tokens per item, almost all of it in proposing, plan review and archiving. The code reviews cost the same in both builds.
  4. A spec reviewer that runs the jar against the PRD did most of what the vibe build needed. It found every contract bug the vibe build fixed. A cheap way to get most of OpenSpec's benefit could be to add "test every numeric guard at its type limits" to that reviewer's brief.
  5. Fix the vibe build's BR-1 bypass by comparing the scale on both sides (scale < -1000 || scale > 1000), with a test at 1E+2147483648. Also decide whether OperandDeserializer's length check stays.
